## 2. 原子 Claim 的事务流程

接口：`claim(run_id: UUID) -> RunRecord | None`。

```text
获取本 Repository 的 SQLite 连接
  → BEGIN IMMEDIATE
  → 按主键读取 status 与完整 record_json
  → 不存在或不是 queued：ROLLBACK，返回 None
  → 从 JSON 恢复 RunRecord
  → 只将 status 改为 running，completed_at 设为 None
  → 条件 UPDATE，同时写入状态、完成时间列和完整 JSON
  → rowcount 不等于 1：ROLLBACK，返回 None
  → 提交事务成功后，返回 running RunRecord
```

实际条件更新：

```sql
UPDATE runs SET status = 'running', completed_at = ?, record_json = ?
WHERE run_id = ? AND status = 'queued'
```

参数分别为 None、修改后的完整 JSON 和 run_id；所有值通过 SQL 参数绑定传入。

BEGIN IMMEDIATE 在读取前取得写事务，使独立连接间的领取串行化；条件 UPDATE 和 rowcount 检查同时保留。不存在、非 queued 或更新未命中时显式 rollback；SQL、JSON 校验或提交等异常由连接上下文回滚并向外传播。成功结果只在退出事务上下文、完成提交后返回。相关事务语义参考 [SQLite 官方事务文档](https://www.sqlite.org/lang_transaction.html) 与 [Python sqlite3 连接上下文文档](https://docs.python.org/3.12/library/sqlite3.html#how-to-use-the-connection-context-manager)。

没有在事务中调用 Planner、Runtime、handler 或 await。原有连接 busy timeout 仍为 1 秒，没有增加数据库自动重试或应用级全局锁。

领取不会重建简化记录。tool_call、result、plan、tool_executions、依赖、结果绑定、answer、error、created_at 等字段通过完整 RunRecord JSON 保留。created_at 列保持不动，completed_at 列与 JSON 同时为空。

## 3. RunService 执行链

```text
POST /runs
  → 保存 queued、加入本实例 asyncio.Queue
  → 返回原有 HTTP 202、queued、run_id、Location

单个长期 Worker 出队
  → execute_run
  → repository.claim(run_id)
      ├─ 成功：使用返回的 running RunRecord，进入原执行链
      │   → Planner → ToolCall / ParallelPlan / DAGPlan
      │   → 原 Runtime 参数校验、超时、重试和异常处理
      │   → 保存步骤、结果、answer、error、completed_at
      └─ 返回 None：只读取数据库当前快照，直接返回
          → 不调用 Planner / Runtime / handler
  → 原 Worker finally 清理 _enqueued_ids，并 task_done

GET /runs/{run_id}
  → 原 Repository 查询路径，返回最新快照
```

删除了 execute_run 原先独立的 get → 检查 queued → 设置 running → save 状态迁移，没有保留两套领取逻辑。未领取但记录存在时，返回 get_run 的深拷贝；记录不存在时仍抛 KeyError。没有把 None 当作可执行记录。

Worker、Queue、生命周期、运行结果汇总、取消保存失败时继续传播 CancelledError 的逻辑保持原样。本地 _enqueued_ids 仅用于单实例队列去重，跨实例的领取排他性由 SQLite 事务提供。

## 6. 已知限制与后续边界

- Claim 是一次 queued → running 的原子迁移，不是 Lease。领取后 Worker 崩溃，Run 仍可能停留 running；不会擅自重置为 queued。
- 没有 owner、心跳、领取代次、fencing_token 或过期回收；下一阶段 M4.2.3 再定义恢复语义。
- save 仍是原来的完整快照 UPSERT，不具备所有者校验，不能据此宣称任意外部写入或旧执行者迟到写入受到 fencing 保护。
- SQLite 仍是同步 I/O、单写事务和原有 1 秒锁等待；长事务、锁竞争或磁盘故障仍可能抛异常。本次短事务竞争通过不代表所有负载下永无 SQLITE_BUSY。
- 沿用现有 Worker 的异常及取消兜底保存策略；本阶段没有增加数据库错误重试或存储故障下的终态写入保证。
- Queue 和本地去重集合仍在各实例内存中。Claim 防止正常竞争者重复进入执行链，没有实现 Dispatcher、跨进程共享队列或完整多 Worker 可靠执行平台。
- 没有 Checkpoint、DAG 步骤恢复、业务幂等键、Inbox / Outbox 或外部消息队列；外部工具副作用与数据库提交不具备事务原子性，也不提供 exactly-once 保证。
- 未接入真实 LLM、RAG 或新工具；设备、告警、流量和诊断继续为 mock。

本阶段验收证据支持：多个独立 SQLite 连接竞争同一条 queued Run 时，恰好一个连接领取成功；服务只有领取成功后才进入现有执行链。不能将这项结论扩大为崩溃恢复或端到端业务幂等保证。
