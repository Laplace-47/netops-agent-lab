## 1. Codex 总结

### 1.1 实现范围

- Run 新增 `queued`，保留 `running / succeeded / failed`；逐工具状态、ToolResult、依赖、绑定、错误和汇总字段继续保留。
- `RunService.create_run()` 只生成 run_id、保存 queued Run、将 run_id 放入 `asyncio.Queue` 并返回深拷贝；不执行 Planner，不为每个 Run 创建独立后台执行任务。
- `RunService.start()` 启动一个名为 `netops-run-worker` 的长期任务。已有活动 Worker 时重复 start 不新增消费者。
- Worker 串行消费 run_id，调用 `execute_run()` 将状态更新为 running，然后复用原有 ToolCall、ParallelPlan、DAGPlan 执行链。并行工具与 DAG 的同批并发继续由原模块负责。
- `POST /runs` 提交后返回 `202 Accepted`、queued 快照及 `Location: /runs/{run_id}`。客户端后续通过 GET 查询最新快照，不再把 POST 的 queued 响应与最终 GET 结果要求为相等。
- `GET /runs/{run_id}` 不执行任务，返回保存记录的深拷贝，可查看 queued、running、succeeded、failed；不存在的 ID 仍为 404。
- 执行正常完成时保存最终 answer、error、结果及 completed_at。Worker 对执行入口逸出的普通异常保存安全的 `INTERNAL_ERROR`，继续消费后续任务。
- 工具/编排子任务自行抛出 CancelledError 时，当前 Run 保存 `failed / CANCELLED`；没有对 Worker 本身发出取消请求时，消费者继续服务。对 Worker 的外部取消则等待原有取消清理后退出。
- FastAPI lifespan 启动和关闭 Worker；测试显式运行 lifespan，没有假设 HTTPX ASGITransport 自动运行它。
- 关闭时停止接收提交，取消当前 Run，等待工具清理；尚未执行的 queued Run 保存为 `failed / CANCELLED` 并设置 completed_at。它们不会再执行 handler。
- 每次成功出队后，无论成功、失败还是取消都在 finally 调用 task_done；关闭时排空的队列项也配平，使 queue.join 可用于测试和队列排空。join 只证明队列项已处理，不表示每个 Run 都成功。

这是同一进程、同一事件循环中的后台消费者，不是独立 Worker 进程。Run 之间按队列顺序串行执行，单个 Run 内仍可执行并发工具/DAG 分支。生产代码只为长期消费者创建任务，未用“每个 Run 一个 create_task”替代队列。

### 1.3 当前执行链

```text
应用 lifespan 启动
  → RunService.start()
  → 创建单个长期 Worker，等待 queue.get()

POST /runs {message}
  → 请求模型校验
  → create_run()：创建 queued Run → 保存 → run_id 入队
  → 返回 queued 深拷贝，HTTP 202 + Location

Worker
  → queue.get() 取出 run_id
  → execute_run()：queued → running
  → 原 Planner
    → ToolCall：原 ToolRuntime
    → ParallelPlan：原 execute_parallel → 各 ToolRuntime
    → DAGPlan：原 execute_dag → 就绪批次/结果绑定 → 各 ToolRuntime
  → 保存 succeeded / failed、结果、answer、error、completed_at
  → finally queue.task_done()
  → 继续消费下一个 run_id

GET /runs/{run_id}
  → 返回最新保存记录的深拷贝，不触发执行

应用 lifespan 关闭
  → 停止接收提交 → 取消活动执行 → 等待清理
  → 未执行队列项记 failed/CANCELLED，设置 completed_at 并配平 task_done
  → Worker 退出
```

Run 状态使用 `queued → running → succeeded/failed`。取消以 `failed` 和 `error.code=CANCELLED` 表达，没有新增 cancelled Run 状态；逐工具记录原有的 cancelled 状态保留。运行中 completed_at 为 null，终态设置完成时间。

## 6. 验收结论、当前限制与后续待办

本阶段五项完成标准均满足：有任务结束前返回的 POST、有 running GET、有 Worker 完成并保存全部 DAG 步骤的证据、有失败后继续消费的证据，且保留的原有用例与新增用例共同通过 172 项完整回归。关闭清理也有 Event/锁断言及临时服务正常退出证据。

已完成代码和这些验证，不等于已提交 GitHub，也不等于具备持久化、多进程或生产运行保证。本轮结束时仍等待审查，没有提交或推送。

当前限制和未验证边界：

- Queue、Run 字典和 Worker 都在单进程内存中；重启或进程崩溃会丢失数据，多个 Uvicorn 进程不共享队列。
- Run 之间只有一个串行消费者；没有队列容量限制、背压、优先级、并发 Run 数配置或存储回收。
- 关闭策略是取消当前执行并把尚未执行项保存为 failed/CANCELLED，不承诺关闭前把所有 queued Run 都执行成功。
- 取消清理依赖 handler 配合。单次外部取消与关闭协程取消已有测试；连续多次取消、吞掉取消的 handler、同步阻塞操作和大规模积压尚未专门验证，不能宣称强制终止任意代码或有固定关闭时限。
- 未新增 Run 取消 HTTP 接口、执行进度订阅、Run 总超时、重试退避或业务操作幂等保证。
- 没有数据库持久化、Lease/Claim、Checkpoint、Outbox 或崩溃恢复。
- 没有真实 LLM、真实网络数据、Redis/RabbitMQ、SSE 或 RAG；流量仍固定为模拟 72.5% / HIGH，不能作为真实网络监控指标。
- 本轮未制作新截图，没有验证跨机器、多进程、长时间稳定性或性能压测；已有证据仅支持本文列出的场景。

后续阶段可分别安排以下工作，本阶段没有实现：

2. 使用原子 Claim 防止多个 Worker 同时领取同一任务；定义 owner、Lease 到期、续期及失效处理。
3. 明确崩溃后的过期任务回收、重试与幂等语义；验证重复领取、旧 Worker 迟到写入和恢复场景。
4. 根据实际需求增加队列容量、并发限制和观测，再规划 Checkpoint 等能力。
