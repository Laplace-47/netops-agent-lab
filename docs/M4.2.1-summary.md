## 2. Repository 设计

### 2.1 接口与表结构

`RunRepository` 是同步 Protocol，提供 initialize、save、get、list_by_status、close。默认实现为 `SQLiteRunRepository`，连接延迟打开：

- 构造 Repository / create_app / 导入 main 时不连接、不创建目录或数据库。
- lifespan 初始化；在生命周期外使用 Repository 的初次 CRUD 也会延迟初始化。
- close 显式释放连接且可重复调用；close 后 CRUD 拒绝使用，需显式 initialize 才能重新打开。
- Repository 限于同一事件循环线程使用，不提供线程池连接管理。

表结构为：

```sql
CREATE TABLE IF NOT EXISTS runs (
    run_id TEXT PRIMARY KEY,
    status TEXT NOT NULL CHECK (status IN ('queued','running','succeeded','failed')),
    created_at TEXT NOT NULL,
    completed_at TEXT,
    record_json TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS runs_status_created_at
ON runs(status, created_at, run_id);
```

save 使用带参数绑定的 INSERT ... ON CONFLICT DO UPDATE，同时更新状态、时间列和完整 record_json。created_at 索引列规范化为 UTC ISO 字符串；状态查询按 created_at、run_id 排序，JSON 保留原模型内容。

`RunRecord.model_dump_json()` 保存完整对象；`RunRecord.model_validate_json()` 读取并恢复 UUID、带时区时间、ToolCall、ToolResult、ParallelPlan、DAGPlan、绑定、逐步骤结果、answer 和 error。get 缺失时抛 KeyError，由原 GET 接口转为 404。每次读取均新建模型，Service 再返回深拷贝，没有权威或伪装用途的 _runs 字典。

### 2.2 事务边界

序列化在写事务前完成。每次 save 的事务只执行一条 UPSERT，函数返回前提交；SQL 失败则回滚。读查询取完数据后返回，不在事务或数据库锁内执行 Planner、Runtime、handler 或 await。

当前使用同步标准库 sqlite3，连接 busy timeout 为 1 秒。短事务不代表磁盘永不阻塞事件循环，也不是针对高吞吐的异步存储实现。未引入 aiosqlite、SQLAlchemy 或 WAL 等额外策略。

## 3. 提交、执行、恢复和关闭

### 3.1 正常执行

```text
POST /runs
  → 创建 queued Run
  → Repository.save 提交完整 queued 记录
  → run_id 加入现有 asyncio.Queue
  → 返回独立 queued 快照、run_id、HTTP 202 与 Location

单 Worker 出队
  → Repository.get
  → 保存 running，提交后才调用 Planner
  → 原 ToolCall / ParallelPlan / DAGPlan 执行链
  → 保存工具调用与执行中的步骤快照
  → 成功、工具错误、未预期异常或取消后保存最终状态、结果、错误和 completed_at
  → finally 配平 task_done 和本实例入队 ID 集合

GET /runs/{run_id}
  → 读取 Repository 最新记录
  → 返回快照；不调用 Planner/handler
```

HTTP 接口、响应模型、202、Location、未知 Run 404 和非法请求 422 保留。仅数据权威来源改变。

为保持执行中的 GET 语义，单工具开始前保存 ToolCall；并行/DAG 初始化记录后保存，并通过可选同步 on_change 在工具开始、完成时保存快照。原 DAG 调度算法没有重写。若保存回调抛错，并发模块取消并等待其他子任务后再传播异常，由 Service 保存安全失败结果；此行为有锁/清理事件测试。

Worker 外层异常和取消路径也通过 Repository 记录失败，不能只在正常返回时保存。如果数据库持续不可用，失败记录本身也可能无法写入；当前记录日志并维持消费者，不回退到内存伪装成功，也不提供数据库故障下的终态写入保证。

### 3.2 queued 启动恢复

启动顺序：

1. initialize 表和索引。
2. Worker 创建前，list_by_status("queued") 查询持久化待执行记录。
3. 用 _enqueued_ids 去重并加入内存队列，避免同一实例在启动前已入队的 Run 重复恢复。
4. 创建单个长期 Worker 消费队列；重复 start 不另建活动消费者。

保存数据库成功、尚未发布到内存队列时进程中断，queued 仍能在下次启动发现。内存队列里的任务随进程退出丢失，也可由数据库重新派发。本地 ID 集合只用于队列去重，不是跨进程 Claim，不是业务幂等键。

本阶段只在启动时恢复，不做 Dispatcher 或运行中定时扫描。恢复时仅选择 queued，**不修改、不执行遗留 running**，避免重复产生可能已经发生的外部副作用。

### 3.3 优雅关闭

lifespan 先调用 Service.stop，等活动执行完成取消清理，再 finally close Repository；启动中途失败也会关闭已初始化连接。

- 已在执行的 Run：保持原取消语义，持久化 failed / CANCELLED、当前已有结果和 completed_at。
- 尚未开始的 queued：只从内存队列取出并配平 task_done，不修改数据库状态，completed_at 仍为空。
- 下个服务实例启动：重新查询 queued 并执行。
- 强制崩溃时 running：允许保持 running；本阶段没有 Lease 或回收逻辑。

这是相对 M4.1 明确要求的关闭语义变化，因此相关旧测试调整了 queued 的预期；活动取消、异步 finally、锁释放、无遗留 Worker 和 join 断言保留。

## 8. 已知限制与下一阶段

- 权威 Run 数据已持久化，但派发仍使用本进程内存 Queue 和单 Worker。
- 可以跨服务实例读取文件记录；**不能据此运行多个 Worker 共享数据库可靠领取**。没有原子 Claim，多个实例可能同时恢复同一 queued 并重复执行。
- 只恢复 queued。崩溃遗留 running 不回收、不重排；不会因保存了步骤结果就具备 Checkpoint 或 DAG 步骤恢复。
- 重复调用 execute_run 时对非 queued 的检查不是跨进程原子状态迁移，不提供 exactly-once、业务幂等或 fencing。
- 长时间不可写、损坏、磁盘满等存储故障可能使终态无法落库；没有备用权威内存、数据库自动重试或 Outbox。
- 使用同步 sqlite3 和完整 JSON 快照；I/O 和锁等待可能阻塞事件循环。尚无大记录/高并发压测、迁移框架、历史保留或容量回收。
- 启动恢复一次性读取所有 queued；没有分页、背压、Dispatcher 或运行中轮询。
- 取消仍依赖 handler 配合；没有强制终止阻塞代码、连续多次取消的完整保证。
- SQLite 文件只保证数据存储，不保证外部工具副作用与数据库提交在同一事务中。
- 未实现 Lease、续租、过期回收、幂等键、Inbox/Outbox、Checkpoint、外部消息队列、真实 LLM、RAG 或新工具。

下一阶段建议独立实现原子 Claim 和 owner/Lease，并用多进程测试验证重复领取、旧 Worker 迟到写入和过期任务回收；随后再定义副作用幂等与崩溃恢复语义。本阶段不提前补上这些功能。

参考公开资料：[Python sqlite3 连接上下文](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager)、[SQLite UPSERT](https://www.sqlite.org/lang_upsert.html)。业务代码和模拟数据为本工程原创实现。
