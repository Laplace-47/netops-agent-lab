# NetOps Agent Lab — M4.2.3 Lease、Heartbeat、过期回收与 Fencing Token

本阶段实现带租约的领取、续租、周期回收和受保护写入。验收重点是：旧执行者失去所有权后，不能通过进度、终态或错误兜底覆盖新执行者的数据。

所有设备、告警、流量与诊断仍为模拟数据。没有接入真实 LLM、外部消息队列或第三方依赖。本文记录本次实现与实际测试；Git 实时状态以实际 Git 命令为准。

## 2. 数据库结构与迁移

在原 runs 表后增加：

```sql
lease_owner TEXT NULL
lease_until TEXT NULL
fencing_token INTEGER NOT NULL DEFAULT 0
```

新增索引 runs_status_lease_until，列为 status、lease_until、created_at、run_id；保留原状态/创建时间索引。

initialize 在短 BEGIN IMMEDIATE 事务内创建基础表、读取 PRAGMA table_info、仅添加缺失列并创建索引。这样既可初始化新数据库，也可迁移 M4.2.2 的五列表，并串行化独立连接同时初始化的迁移。失败时回滚、关闭刚打开的连接；重复初始化不重复添加字段。

Lease 时间通过内部时钟转换为 UTC，以固定六位微秒的 ISO 8601 文本保存，比较使用相同格式。领取资格采用 lease_until <= now；续租和受保护保存必须 lease_until > now。时间在取得写事务之后读取，避免等待写锁前取得的旧时间被误用。Repository 可注入带时区的 clock，测试用同一个可控时钟模拟精确到期。

三个执行控制字段不进入 RunRecord JSON 或 HTTP 响应。RunClaim 是冻结的数据类，包含 run、owner_id、fencing_token、lease_until；身份字段不可重新赋值，内部 RunRecord 快照仍可用于汇总执行结果。续租后的权威期限以数据库为准，不依赖原 RunClaim.lease_until 的初始值。

旧库的 running 且 lease_until 为 NULL 不具备可证明的过期租约，不自动恢复，不修改为 queued。默认 token 为 0；首次有租约领取变为 1。终态、续租和兼容 save 都不重置 token。

迁移方式参考 [SQLite ALTER TABLE 文档](https://www2.sqlite.org/lang_altertable.html)；实际幂等性和失败回滚由本次自动化测试验证。

## 3. Repository 事务与写入保护

### 3.1 claim(run_id, owner_id, lease_seconds)

```text
BEGIN IMMEDIATE
  → 读取状态、完整 JSON、lease_until、fencing_token
  → 仅允许 queued，或有期限且已经到期的 running
  → queued：保留完整业务快照，仅进入 running
  → 过期 running：保留 run_id/message/created_at，清空旧执行状态，从头重跑
  → token + 1，写入新 owner、UTC 期限、running JSON、completed_at=NULL
  → 条件 UPDATE 校验旧 token 与领取资格，检查 rowcount == 1
COMMIT 成功后返回 RunClaim
```

不存在、终态、有效 running 租约、历史无租约 running 均返回 None，并结束事务。SQL 或模型校验等异常向外传播且回滚。SQLite INTEGER 达到上限时拒绝继续递增，避免 token 精度退化。

过期接管会清空 tool_call、result、plan、tool_executions、answer、error 和 completed_at。它是整个 Run 的重新执行，不是恢复旧协程现场，也不是 DAG Checkpoint。

### 3.2 renew_lease

短事务中的条件 UPDATE 同时约束 run_id、status=running、owner、token 和尚未过期的 lease_until。命中一行才更新期限并返回 True；不命中回滚并返回 False。已到期的旧 owner 即使没有接管者，也不能靠续租复活原 token。

### 3.3 save_claimed

所有执行中的写入在一个短写事务内通过以下条件更新：

```sql
WHERE run_id = ?
  AND status = 'running'
  AND lease_owner = ?
  AND fencing_token = ?
  AND lease_until > ?
```

状态、created_at、completed_at、完整 record_json 在同一 UPDATE 中保存，rowcount 必须为 1，否则抛 LeaseLostError 并回滚。禁止将执行状态写回 queued。

- 中间 running 快照保留 owner 和期限。
- succeeded/failed 终态同时清空 owner 和期限，保留最后的 token。
- 即使本地尚未收到心跳失效通知，数据库也会拒绝已经过期或被替代的旧 token。
- 不存在退回普通 save 的分支。

save 保留原有非执行者兼容用途，例如创建 queued。Service 中唯一的普通 Repository.save 调用位于 create_run；Planner 之后的进度、最终成功、业务失败、取消和错误兜底均走 save_claimed。

### 3.4 Claim 前的异常

新增 fail_if_queued(run_id, error)，在短事务内读取并条件更新仍为 queued 的记录。若其他实例已经领取为 running，或任务已完成，则不更新。数据库不可用时记录日志，不伪称终态已经可靠保存。

list_reclaimable 返回 queued 及有租约且已到期的 running，不会返回历史无租约 running。

所有事务内均没有 Planner、Runtime、handler 或 await。SQLite 连接仍使用原来的 1 秒锁等待，同步 I/O 的限制保留。

## 4. Worker、Heartbeat 与 Reaper

默认配置：

| 配置 | 默认值 | 校验 |
| --- | ---: | --- |
| lease_seconds | 30.0 秒 | 有限正数，不接受 bool |
| heartbeat_interval | 10.0 秒 | 有限正数，必须小于 lease_seconds |
| reaper_interval | 1.0 秒 | 有限正数，不接受 bool |

每个 RunService 生成一个独立 UUID worker_id。POST 仍然只保存 queued、入 Queue，返回原有 HTTP 202 / Location，不直接为请求启动执行任务。每个实例仍由单个长期 Worker 派发。

Worker 成功 Claim 后，为当前活动 Run 创建受管理的执行子任务和心跳子任务。拆分这两个子任务用于失租时取消执行、等待清理；没有用逐 HTTP 请求 create_task 代替 Queue/Worker。

```text
Queue 出队
  → 从 _enqueued_ids 移除，加入 _active_ids
  → Claim(owner_id, lease_seconds)
      ├─ 未领取：返回数据库快照，不调用 Planner / Runtime / handler
      └─ 领取成功：
          ├─ 执行原 ToolCall / ParallelPlan / DAGPlan
          │   → _save_execution → save_claimed
          └─ 心跳按间隔 renew_lease
              → False 或异常：标记失租，取消执行并等待清理
  → 清理执行和心跳任务
  → Worker finally 清理活动 ID，并 task_done
```

start 先查询可回收任务，再启动单个 Worker 和单个 Reaper。重复 start 不另建正常活动任务；若某个后台组件已经结束，重启会补建组件，并先取消、等待不再适用的旧回收器。补充测试曾复现该路径的两个生命周期问题，修复后通过。

Reaper 周期查询 list_reclaimable，按本实例队列集合去重。_enqueued_ids 现在只表示仍在 Queue 中的 ID；_active_ids 表示正在处理的 ID。因此过期活动任务可以再次入队，而不会被活动 ID 永久挡住。最终能否接管仍由数据库 Claim 决定。

stop 停止 Worker、Reaper 和活动执行的父任务，等待执行与心跳清理，再排空内存 Queue、配平 task_done。正常持有租约的活动任务按原规则保存 failed/CANCELLED；未开始的 queued 仍留在数据库。连接继续由原 FastAPI lifespan 在 Service 清理完成后关闭。

提交前复查复现了重复取消漏洞：关闭协程连续收到取消时，旧实现可能提前结束，lifespan 随即关闭连接，而 handler 和心跳仍在清理。直接重复取消 Worker 也可能再次打断 handler 的异步清理。修复后，execute_run 通过 shield 隔离父任务的自动取消传播，再显式请求一次执行取消；_wait_for_cleanup 循环等待清理完成，记录期间收到的取消，最后继续传播 CancelledError。stop 同样使用这个等待函数，不会因第二次取消而提前关闭资源。

## 5. 取消与异常边界

| 来源 | 处理与数据库行为 |
| --- | --- |
| 服务关闭 / 执行父任务被外部取消 | 传播 CancelledError；仍持有租约时受保护保存 CANCELLED，等待 handler、心跳和子任务清理 |
| handler 自行抛 CancelledError | 当前 Run 受保护保存 CANCELLED；父 Worker 本身没有取消请求时继续处理后续任务 |
| 心跳返回 False | 先设置失租标记，再取消执行；转换为 LeaseLostError，跳过通用失败兜底 |
| 心跳抛数据库异常 | 无法证明所有权，采取同样的停止策略并记录日志，不继续写执行状态 |
| save_claimed 抛 LeaseLostError | 设置本地失租标记、清理其他执行分支，不保存错误终态，不覆盖新 owner |
| 普通执行错误 | 保留原安全错误分类；所有保存都带 owner/token/有效期检查 |
| Claim 前普通异常或自行取消 | 只能 fail_if_queued，不能改写其他 owner 的 running 或终态 |

失租标记阻止已明确失去所有权的执行者再发出保存；SQL 条件负责防御尚未发现失租的执行者。两层都存在，不把本地标记当作跨实例锁。

同时发生外部取消和失租时，旧数据写入仍被拒绝，并保留外部 CancelledError，避免 Worker 因取消被改写成普通错误而继续等待队列。取消清理完成后再传播的原则参见 [Python asyncio 任务取消文档](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)。

## 9. 限制与尚未验证的边界

- 过期接管从头重跑整个 Run；没有 Checkpoint 或 DAG 步骤级恢复。
- 历史 running 且无 lease_until 不自动重跑，需要人工识别和后续明确迁移策略。
- Fencing 保护遵守 owner/token/期限校验的数据库写入。兼容 save 仍是无条件 UPSERT，非执行者误用它不在 fencing 保护范围内；Worker 执行链已经统一走 save_claimed。
- 不能撤销已经发出的外部请求，不能保证真实外部副作用只发生一次；没有业务幂等键、Inbox/Outbox 或 exactly-once。
- 取消依赖 handler 正确配合；同步阻塞或长期拒绝取消的代码不能被 asyncio 强制终止。当前不是隔离进程执行器。
- SQLite 是同步 I/O、单写事务、1 秒锁等待；没有跨主机时钟偏差、大规模积压、磁盘满、长锁竞争或持续存储故障的压力验证。无法写入时不能保证终态一定落库。
- 回收器按间隔扫描，没有分页、背压、持久消息队列或 Dispatcher。
- 新的过期回收验证使用可控时钟、独立连接和两个独立应用实例；没有把该证据包装成真实进程崩溃现场恢复。
- 未接入 Redis、RabbitMQ、Celery、真实 LLM、RAG 或新业务工具。README 和历史总结的阶段说明按本任务要求留给后续文档修正。
